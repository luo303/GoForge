# MindOS 开发计划

本计划以**质量与验收完成度**为进度，不设置工期，不以提交数量衡量速度。原 Phase 1–8 拆为 Phase 1–21，每个阶段只增加一层可独立验证的能力。

**2026-11-10 调整（用户决策）**：阶段粒度从"每层最小可验证能力"改为**"一个阶段 = 一个功能，且做完整做可靠"**。不再接受"先最小化实现、细节以后补"的收尾方式；确实都很小、彼此相关的功能可以合并进同一阶段。已完成的 Phase 1–5 不按新标准返工，只补已登记的已知尾巴。模块顺序不变，仍不设工期。

## 1. 执行原则

1. **顺序推进**：默认不跨阶段开发；后续阶段不得替前期补测试、补错误处理或补文档。
1. **一个阶段一个功能**：阶段按"用户可感知的一个完整功能"划分，前后端、测试、故障演练在同一阶段内交付，不做"本阶段只有 API、界面以后再说"的半截阶段。
1. **不做占位实现**：功能范围内的路径一次做全（含空态、加载态、失败态、重试与取消入口）。确实超出本阶段功能的相邻能力，写进「后置增强」并注明触发条件，而不是留个半成品在页面上。
2. **小步提交**：下列提交拆分是最小建议，可继续拆细，不把多个独立行为揉成一次提交。
3. **先设计后实现**：涉及数据模型、模块边界或执行语义时，先改 `docs/design/overview.md`，再写代码。
4. **先正常后异常**：每个能力除了成功路径，还必须验证参数错误、依赖不可用、重复执行和取消/恢复。
5. **不带债收尾**：编译通过不代表完成；阶段声明的自动化测试、故障验证、页面验收和文档更新全部完成才算完成。
6. **不拿真实模型做脆弱测试**：自动化测试使用本地假 HTTP 服务或测试替身；真实模型只做可重复的冒烟与质量评测，不断言逐字回答。
7. **数据库不降级**：repository 与迁移测试使用真实 PostgreSQL/pgvector，不用 SQLite 替代，避免方言与并发行为失真。

## 2. 固定质量门禁

后端每个阶段都执行：

```bash
cd backend
go build ./...
go vet ./...
go test -race -count=1 ./...
```

前端自 Phase 3 起执行：

```bash
cd frontend
npm run lint
npm run test
npm run build
```

按阶段能力补充以下测试层次：

| 层次 | 必须覆盖的内容 |
|---|---|
| 单元测试 | 纯函数、状态机、边界值、错误分支；bug 修复必须带回归测试 |
| 数据库集成测试 | 迁移、约束、事务、条件更新、并发领取、回滚；使用真实 PostgreSQL |
| HTTP 契约测试 | 统一信封、状态码、参数校验、错误码、request_id |
| 前端测试 | 关键交互、空态、加载态、失败态；不只测组件能渲染 |
| 故障注入 | 模型超时、进程重启、连接断开、重复消息、依赖宕机 |
| AI 质量评测 | 固定小样本集；检查引用、结构、召回与约束保留，不断言模型逐字输出 |

每个阶段收尾时，在对应章节记录实际执行的命令、代表性 curl / 页面结果、已知限制；遗留问题同步到 `AGENTS.md`。

### 阶段完成的六条标准（2026-11-10 起，Phase 6 及以后强制执行）

一个阶段要宣布完成，六条必须同时成立，缺一条都不算完成：

1. **功能闭环**：用户能在界面上走完该功能的全部路径，含空态、加载态、失败态；不是只有 API 可调。
2. **失败可解释**：每类失败有明确错误码与中文提示，不出现 `500 + internal error` 让人去翻日志。
3. **故障演练**：把该功能依赖的故障真的制造一遍（停库、停 MinIO、`kill -9`、模型超时/限流），验证状态可恢复、不留半截数据，并把演练过程写进验收记录。
4. **并发与重复**：双击、刷新重进、重复提交、并发操作都不产生脏数据，且有用例守着。
5. **测试与门禁**：单测 + 真库集成 + 前端用例齐备，`go build/vet/test -race` 与 `lint/tsc/test/build` 全绿。
6. **文档同步**：本文件写验收记录，`docs/design/overview.md` 同步，关键取舍落进代码注释。

## Phase 1 工程基线纠偏（已完成，2026-11-08）

**目标**：先把现有骨架中的确定性缺陷修掉，建立后续所有阶段共用的测试习惯。

**范围**：中间件顺序、非法配置报错、关键错误路径回归测试、启动与排错说明。

**提交拆分**
1. `fix: 修正中间件顺序使 panic 请求保留访问日志`
2. `test: 补充 panic 日志与 request_id 回归用例`
3. `fix: 配置解析失败时启动报错`
4. `test: 补充配置边界与非法值用例`
5. `docs: 完善本地启动与常见故障说明`

**质量验证**
- panic 请求同时有访问日志、stack、request_id，客户端不收到内部堆栈。
- 非法整数/时长、空密码、非法日志级别均启动失败；未设置的普通默认值仍正常。
- 重复运行测试无端口与全局状态污染，`-race` 通过。

**退出标准**：`AGENTS.md` 中两个已知代码问题关闭，且都有“旧实现会失败”的回归测试。

## Phase 2 数据迁移与系统状态（已完成，2026-11-09）

**目标**：建立可信的数据库变更机制；后续加表不再依赖手工 SQL。

**范围**：`migrations/`、`cmd/migrate/`、pgvector 扩展、存储与模型配置校验、`/system/status`、只读设置接口。

**提交拆分**
1. `feat: 引入 SQL 迁移与迁移执行入口`
2. `feat: 启用 pgvector 扩展并记录迁移版本`
3. `feat: 新增模型、存储与预算配置校验`
4. `feat: 新增系统状态与只读设置接口`
5. `test: 覆盖迁移回滚与脏版本恢复`
6. `docs: 编写迁移操作与恢复说明`

**质量验证**
- 空库执行 `up → down → up`；重复 `up` 不重复建表。
- 中断迁移后能识别 dirty 状态，文档中的恢复步骤经过实测。
- `/system/status` 分别报告数据库、vector 扩展、迁移版本；模型未配置时显示未配置，不伪造连通成功。
- 密钥只返回脱敏结果，日志与响应均不泄露 `.env` 内容。

**退出标准**：全新环境只按 README 即可完成迁移；状态接口能准确定位“库不通、扩展缺失、迁移落后”三类问题。

**质量验证**

## Phase 4 文本文档入库（已完成，2026-11-09）

**目标**：完成最小的 Knowledge 垂直切片：文本进来，解析、切分、落库、可见。

**范围**：documents/document_chunks、文件存储、Markdown/TXT 解析、标题/段落切分、文件与笔记同步导入、基础列表/详情/分块页。

**提交拆分**
1. `feat: 新增文档与分块模型及迁移`
2. `feat: 实现本地文件存储与内容哈希`
3. `feat: 实现 Markdown 与纯文本解析`
4. `feat: 实现保留偏移的分块器`
5. `feat: 实现文件与笔记同步导入接口`
6. `feat: 实现文档列表详情与分块预览`
7. `test: 覆盖解析切分与入库事务边界`

**质量验证**
- 标题、空段落、超长段落、代码块、中文与 emoji 的偏移准确。
- 入库任一步失败时事务回滚；孤儿文件有明确清理策略并经过测试。
- 列表分页、非法文件类型、超大文件、空笔记均返回约定错误。
- 此阶段不要求 embedding 和搜索，页面明确显示尚未索引。

**退出标准**：一个 Markdown 文件和一条笔记可从页面上传并查看全部分块，分块能精确映射回原文。

**验收记录（2026-11-09）**

- 迁移：`go run ./cmd/migrate up` 在已有 Phase 2 的开发库上从版本 1 升到 2，`documents` 与 `document_chunks` 一次建全（含 `content_hash` 唯一索引、`(document_id, seq)` 唯一、`tsv` 生成列、`embedding vector(1536)`）。
- 接口实测（`HTTP_ADDR=:18080` 起服务，避开已被占用的 8080）：笔记与文件均返回 201；列表 `total=2`；分块 `[0,67)`、`token_count` 有值；错误路径返回 415（.pdf）、400（空笔记）、404（不存在）、409（同内容重复导入）。
- 偏移正确性：`[]rune(text)[start:end]` 逐字等于分块内容；中文与 emoji 按 1 个码点计；CRLF、无收尾围栏、超长无标点段落都有确定行为。
- 事务边界（真实库集成测试）：分块违反 CHECK 时整笔回滚，`documents` 不留空记录；重复 hash 翻译为 `ErrDuplicate`；删除文档时级联清空分块。
- 落盘失败补偿：写库失败时删除本次新写文件；内容已存在（`Reused`）时不删，避免把更早文档的原文删掉。存储按 SHA-256 内容寻址，重试不会产生副本。
- 门槛：`go build ./...` / `go vet ./...` / `go test -race -count=1 ./...` 全绿；前端 `lint` / `test`（24 用例）/ `build` 全绿。
- 与设计的两处偏差：① `GET /documents` 本阶段只做 `limit` / `offset`，`collection` / `tag` / `status` 筛选随 Phase 5 的标签能力一起做（没有写入方的筛选条件无法验收）；② 偏移单位改为**码点**而不是设计文档原写的"字符"，实现与文档已同步。
- 已知限制：分块不设重叠（等 Phase 8 有召回评测数据再定）；`token_count` 是估算值（CJK 1 token/字，其余 4 字符/token），Phase 7 接真实分词器；知识页未做分块翻页（超过 100 块只显示前 100 块并提示）；窄屏布局仍未人工目视验收。

## Phase 5 文档管理可靠性（已完成，2026-11-09）

**目标**：把导入从“传一次就定型”变成可反复操作的文档管理。

**范围**：重复导入复用既有文档、删除、重索引、分类与标签筛选。**多格式（PDF、网页）已移出主线**，理由见文末「后置增强」。

**提交拆分**
1. `feat: 实现文档幂等导入与重复检测`
2. `feat: 实现文档删除与重新索引`
3. `feat: 实现分类标签与列表筛选`
4. `test: 覆盖重复导入、删除与重索引`

**质量验证**
- 相同内容重复上传返回既有文档（200，带 `existed: true`），不产生第二组分块，也不多存一份文件。
- 重索引用新结果整体替换：先算完新分块，再在同一事务里删旧插新；失败时旧数据完整保留。
- 删除在同一事务内清 documents（分块级联），提交后才删原始文件；文件删除失败只记日志，不回滚已提交的事务。
- 重复删除返回 404，不留孤儿行；同内容文档只有一条，删除不会误删他人的原文。

**退出标准**：文件与笔记两种来源都能重复导入、删除、重索引、打标签；重复上传、重复删除、连续重索引不产生孤儿文件或孤儿行。

**与原计划的偏差**：原计划含 PDF 文本层与网页正文抽取，2026-11-09 决定移出主线。原因是它们必然引入首个第三方解析依赖（或系统包），而收益与当前主线（检索、Agent）无关，属于产品化之后的可选增强。

**验收记录（2026-11-09）**

- 迁移：**本阶段不需要新迁移**。`collection` / `tags` 在 0002 里就一次建全（含 `tags` 的 GIN 索引），本阶段只是把它们从"预留列"变成真正读写。
- 幂等导入实测（`HTTP_ADDR=:18080`）：同内容第二次 `POST /documents/note` 返回 **200 + `existed:true`**，`id` 与首次相同、标题仍是首次的标题；首次返回 201。文件导入同理，且不产生第二份原文件。
- 标签与分类：`text[]` 在 GORM 下**必须自定义类型**——`[]string` 写入会报 `expression is of type record`、读取会报 `unsupported Scan ... into *[]string`，两条实测结论写在 `internal/knowledge/string_array.go` 文件头；`Value`/`Scan` 成对实现并有往返用例守着引号、反斜杠、空格、中文。
- 筛选实测：`?tag=go` 命中 1 条，`?tag=nope` 返回空列表且 `total=0`（不是 404），`?status=bogus` 返回 400 并列出合法取值；列表与总数共用同一份条件。
- PATCH 实测：`{"collection":"","tags":["归档"]}` 清空分类（落库为 NULL）并替换标签；`{}` 返回 400；不存在的 id 返回 404。
- 删除实测：返回 `200 + {"id":4}`，第二次删除 404；分块由外键级联删除（真实库集成测试断言无孤儿行）；文件删除失败只记 warn、不回滚已提交的事务（单测制造删除失败）。
- 重索引实测：`POST /documents/4/reindex` 返回重算后的 `chunk_count`；替换失败时旧分块完整保留，缺原文时返回 409 而不是 500。
- 门槛：后端 `go build ./...` / `go vet ./...` / `go test -race -count=1 ./...` 全绿；`MINDOS_TEST_DSN` 指向真实 PostgreSQL 时 7 个集成用例通过（新增 5 个）；前端 `lint` / `test`（31 用例）/ `build` 全绿。
- 三处由本阶段定下的语义：① 幂等命中**不做任何写入**（不合并标签），改元信息走 PATCH——否则"同内容即同一条记录"这个前提会失效；② 删除返回 `200 + {"id":n}` 而不是 204，保持所有响应都走统一信封；③ 缺原文重索引映射为 409，它是数据状态问题而非参数错误。
- 前端按约定先拆分再加功能：`pages/knowledge.tsx`（319 行）只做编排，列表、详情、筛选栏、笔记表单、格式化各自成文件，`CONVENTIONS.md` 的示例已同步。
- 已知限制：`collection` 没有建索引（单用户数据量下全表扫描可接受，真变慢时再加）；重索引是同步请求，10 MiB 文档会占住一条连接，P6 异步化后一并解决；网页导入仍未接。

## Phase 6 本地异步任务（已完成，2026-11-10）

**目标**：将耗时导入与重索引移出 HTTP 请求，靠 PostgreSQL 建立可恢复的任务语义，并把任务状态做成知识页里能看、能操作的功能，不急于引入 MQ。

**范围**：jobs 表与状态机、进程内 worker、条件领取与租约续约、退避重试与错误分类、取消传播、启动与周期补扫、文档导入/重索引切换为 202 + job_id、知识页内的任务进度与失败原因展示、取消与手动重试入口。

**边界**：任务状态**嵌在知识页**（文档行内状态、详情页错误与重试），不占用 `/tasks` 页面——`/tasks` 规划给 Phase 17 的个人目标/计划/待办，与系统后台作业不是一回事。本阶段不做通用任务中心，不接 MQ。

**提交拆分**
1. `feat: 新增异步任务模型与迁移`
2. `feat: 实现任务条件领取与租约续约`
3. `feat: 实现进程内 worker 与优雅停止`
4. `feat: 实现任务补扫与崩溃恢复`
5. `feat: 文档导入与重索引切换为异步任务`
6. `feat: 实现任务重试取消与失败原因接口`
7. `feat: 知识页展示任务进度并支持取消重试`
8. `test: 覆盖并发领取、故障注入与进程重启恢复`

**质量验证**
- 多 worker 并发时同一 job 只被一个领取；重复提交有 dedupe 行为（部分唯一索引兜底，不靠应用层先查后插）。
- worker 宕机后过期租约可被接管；补扫不只跑在启动时，周期补扫也要覆盖"别的实例还挂着"的场景。
- 续约失败（影响 0 行）时 worker 必须放弃执行，不允许两个 worker 同时写同一文档的分块。
- 取消能传播到解析过程；达到 max_attempts 后停止重试并保留错误码；`ErrUnsupportedType` 这类不可恢复错误直接 failed，不空转重试。
- HTTP 202 返回 document 与 job_id；幂等命中仍返回 200 + existed，不新建任务。
- 页面上传后立即看到"处理中"，失败行显示中文原因并提供重试/取消；刷新页面后状态不错乱，轮询在终态自动停止。

**故障演练（必须实际执行并记录）**
1. 任务跑到一半停 PostgreSQL：job 可解释地失败或等待，恢复后能被重试到终态。
2. 任务跑到一半停 MinIO：原文读取失败有明确错误，文档不处于"看起来成功"的状态。
3. `kill -9` 服务进程再重启：running 任务经租约过期回到 queued 并跑完，不出现永远 running。
4. 运行中点击取消，再刷新页面：状态一致，不回到 running。

**退出标准**：上述四类故障演练全部通过且任务状态可解释、可恢复；六条完成标准同时满足。

**验收记录（2026-11-10）**

- **迁移**：`0003_jobs`，一次建全而不是逐阶段加列。三处约束/索引各有明确用途：状态机 CHECK、部分唯一索引 `(kind, dedupe_key) where status in ('queued','running')` 负责去重、`(run_after)` 与 `(lease_expires_at)` 两条部分索引让领取与补扫只扫"待办"。
- **契约**：`POST /documents`、`/documents/note`、`/documents/:id/reindex` 均改为 **202 + job_id**，文档先落 `pending` / `indexing`；`POST /documents/:id/cancel` 返回 200 + 文档状态，没有进行中的处理时 409。幂等命中仍是 200 + `existed`，且不建任务。
- **队列语义**：领取用一条 `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1)`，判断与改状态同一条语句；`attempts` 在领取时 +1（崩溃那次也算尝试）；心跳每 `lease/3` 一次并回报状态；退避 3s·2^n 封顶 5 分钟并叠加 ±25% 抖动；不可恢复错误（类型不支持、编码错误、元信息非法、原文丢失、文档不存在、任务类型未注册）直接判失败，不占重试名额。
- **任务与文档的两次同事务写入**：`CreateWithJob`（文档 + 任务）与 `FinishImport`（换分块 + 置 ready）。前者避免"有文档没任务"，后者避免"显示成功但内容是空"。
- **错误可解释**：`documents.error_code` 与 `jobs.last_error_code` 记同一个码（业务错误实现 `JobErrorCode`，worker 只搬运）。已有码：`unsupported_type`、`empty_document`、`not_utf8`、`invalid_metadata`、`source_missing`、`storage_unavailable`、`document_not_found`、`cancelled`、`process_failed`。前端详情页在失败时就地显示原因。
- **故障演练（2026-11-10 20:19 起，隔离库 `mindos_drill`，服务跑在 `:18080`）**

| 演练 | 操作 | 观察结果 |
|---|---|---|
| kill -9 | 导入返回 202 后立刻 `kill -9`，重启 | 任务从 `queued/a0` 继续，重启后 `succeeded/a1`，文档 `ready` |
| 执行中死亡 | 直接插入一条 `running` + 租约过期 10 分钟的僵尸任务，重启 | 补扫 1 次将其收回，另一 worker 领走并 `succeeded`，文档 `ready` |
| 停 PostgreSQL | 服务运行中 `docker stop mindos-postgres`，2 秒后恢复 | 进程不退出；`healthz=200`（存活不看依赖）、`readyz=503`；worker 12 次领取失败只 warn；恢复后 `healthz=200`、导入返回 202 |
| 停 MinIO | 上传文件后 `docker stop mindos-minio`，再发起重索引 | 重试 2 次后任务 `failed`、`attempts=3`，任务与文档的 code 都是 `storage_unavailable`；恢复 MinIO 后重新切分成功，`ready` 且 `chunk_count=1` |
| 运行中取消 | 导入后立刻取消 | 返回 200；任务 `cancelled`；文档 `failed` + `cancelled` + 0 分块，两秒后状态不再变化 |

- **演练中修掉的两个真实缺陷**：① 原先取消直接写 `failed`，若 worker 刚好写完分块，会留下"失败但有分块"的半状态；改为运行中只标 `cancelling`，终态由 worker 停下后回调写，回调发现分块已存在则保留成果置 `ready`。② 原先 MinIO 不可用被记成 `handler_error` / `process_failed`，看不出是存储问题；新增 `ErrStorageUnavailable` 与 `storage_unavailable` 码，并让任务表复用同一码。
- **门禁**：后端 `go build ./...` / `go vet ./...` / `go test -race -count=1 ./...` 全绿；带 `MINDOS_TEST_DSN` 时真实库集成用例通过（job 包新增退避、取消、接管；knowledge 包新增两段式、失败原因、取消收尾）。前端 `lint` / `test`（41 用例）/ `build` 全绿。
- **已知限制**：① worker 只在进程内，多实例靠租约互斥而不是分区，规模上去后需要按 kind 分队列；② 空闲时仍按 `JOB_POLL_INTERVAL`（默认 500ms）轮询，Phase 16 换成 MQ 唤醒；③ 按 `payload->>'document_id'` 取消会全表扫 jsonb，单用户量级可接受，任务表变大后需要加表达式索引；④ kill -9 演练中任务恰好已完成（`queued` 状态被杀），"执行中死亡"的真实接管由僵尸任务那一条覆盖；⑤ 取消与完成赛跑时，若内容已写完则保留成果（`ready`），此时任务记 `cancelled`、文档记 `ready`，两者语义不同但都如实。

## Phase 12 记忆召回与质量评估

**目标**：召回不仅“有相关”，还要可解释、可限制、可回归。

**范围**：kind 过滤、向量/重要性/新鲜度打分、top_k 与 token 截断、召回统计、调试接口与评测集。

**提交拆分**
1. `feat: 实现记忆召回打分与过滤`
2. `feat: 实现召回预算与统计更新`
3. `feat: 实现召回调试与来源展示`
4. `test: 建立记忆召回质量回归集`

**质量验证**
- archived/superseded 不参与召回；kind 与 query 空值行为明确。
- 分数各分项可在调试接口查看；top_k 与字符/token 上限不可被客户端无限放大。
- 并发召回统计不会丢更新；统计更新失败不泄露内部错误。
- 评测覆盖相关记忆、相似但冲突记忆、无关记忆和预算不足。

**退出标准**：固定查询的召回顺序与理由可复现，进入后续 Agent 的记忆数量与长度都有硬上限。

## Phase 13 会话与 Agent 最小闭环

**目标**：先跑通不带工具的对话运行时，分离 chat 与 agent，避免一次性引入全部复杂度。

（"最小闭环"指的是**功能边界**——本阶段不带工具与审批；验收标准不降级，仍须满足六条完成标准。Agent 段维持 P13–P16 四个阶段，不合并。）

**范围**：conversations/messages/agent_runs/agent_events、Eino Runner 最小封装、SSE、基础 Chat 页面、断连取消。

**提交拆分**
1. `feat: 新增会话消息与运行事件模型`
2. `feat: 实现会话与消息管理接口`
3. `feat: 接入 Eino Runner 最小对话链路`
4. `feat: 实现事件落库与 SSE 推送`
5. `feat: 实现基础对话页面`
6. `test: 覆盖事件顺序与断连取消`

**质量验证**
- 同一 run 事件 seq 连续且唯一，先落库再推送；刷新后消息仍在。
- 浏览器断连后 run 在约定时间内 cancelled，模型流与 goroutine 均退出。
- chat 包不 import eino，agent 包不 import gin。
- 此阶段只做最近消息窗口和普通对话，不提前实现工具、审批与上下文摘要。

**退出标准**：一次真实模型对话可从页面发起、流式显示、落库、刷新恢复；断开连接不会遗留运行中的 run。

## Phase 14 工具与运行安全

**目标**：给 Agent 加上受控的只读能力与不可绕过的资源上限。

**范围**：search_knowledge/read_document/search_memory、参数校验、tool_audits、max_steps/token/timeout、主动取消、执行轨迹、对话后记忆提炼。

**提交拆分**
1. `feat: 注册知识检索与文档读取工具`
2. `feat: 注册记忆召回工具`
3. `feat: 实现工具审计与运行轨迹`
4. `feat: 实现步数预算与整体超时`
5. `feat: 实现主动取消与对话后记忆提炼`
6. `test: 覆盖工具越界与三重上限`

**质量验证**
- 非法 JSON、负数 top_k、超长返回、模型伪造参数不会穿透到 repository。
- 预算在每次模型调用前检查；100 token 小预算不会继续发起下一次调用。
- 达到步数、预算、超时、主动取消分别落不同 error_code，部分输出与审计保留。
- 对话结束只触发一次 memory_extract，失败不反向破坏已完成回答。

**退出标准**：Agent 能使用知识与记忆回答；所有工具调用有审计，四种终止路径均通过自动化与日志验证。

## Phase 15 Checkpoint 与人工审批

**目标**：实现真正可恢复的 Human-in-the-loop，而不是内存里等待一个 HTTP 请求。

**范围**：agent_checkpoints、agent_approvals、save_memory 写工具、批准/拒绝/过期、Resume、事件断点续传与审批卡片。

**提交拆分**
1. `feat: 实现 Agent Checkpoint 存储`
2. `feat: 新增审批模型与状态机`
3. `feat: 实现 save_memory 审批门`
4. `feat: 实现审批后恢复与事件续传`
5. `feat: 实现审批卡片与执行回放`
6. `test: 覆盖重启恢复与审批并发`

**质量验证**
- 批准后只执行一次写操作；拒绝后模型收到拒绝观察且记忆不落库。
- 两个并发审批请求只有一个生效；过期审批不能恢复。
- 进程在 waiting_approval 状态重启后仍可 Resume；checkpoint 损坏时安全失败。
- SSE 从 since_seq 重连不重复、不漏事件，前端可完整回放。

**退出标准**：写操作没有绕过审批的路径；批准、拒绝、过期、重启恢复四条链路均实测通过。

## Phase 16 MQ 与后台可靠执行

**目标**：在已有 jobs 真相模型上增加 RabbitMQ 唤醒与后台 workflow，不推翻前期任务语义。

**范围**：outbox_events、relay、MQ 消费者、幂等与重投、死信、后台只读 workflow、队列状态与设置展示。

**提交拆分**
1. `feat: 实现事务 Outbox 与投递中继`
2. `feat: 接入 RabbitMQ 任务派发`
3. `feat: 实现幂等消费与失败重投`
4. `feat: 实现死信与队列状态观测`
5. `feat: 实现后台 workflow 运行入口`
6. `test: 覆盖消息丢失重复与 broker 重启`

**质量验证**
- 业务提交成功但 MQ 不可用时有 outbox 补投；消息丢失靠 jobs 补扫兜底。
- 同一消息重复投递不重复执行副作用；broker 重启后任务最终可完成。
- 死信可查看原因并人工重投；relay/consumer 停止时不丢未确认消息。
- 后台 workflow 不随 SSE/HTTP 断连取消，与前台 react 的生命周期明确区分。

**退出标准**：文档入库与后台 workflow 都走统一可靠任务链路；DB、MQ、进程分别故障时均有恢复验证。

## Phase 17 Action 领域与任务管理

**目标**：让目标、计划、任务先成为可独立使用、规则完整的产品模块。

**范围**：goals/plans/tasks/task_dependencies/task_events、状态机、依赖环检测、任务板、目标计划与 Tasks 页面。

**提交拆分**
1. `feat: 新增目标计划任务模型及迁移`
2. `feat: 实现目标计划与任务管理接口`
3. `feat: 实现任务状态机与事件记录`
4. `feat: 实现任务依赖与环检测`
5. `feat: 实现 Tasks 页面与任务看板`
6. `test: 覆盖状态流转依赖与删除边界`

**质量验证**
- A 依赖 B、B 依赖 A 等直接与间接环均被拒绝；自依赖同样拒绝。
- 依赖未完成时不能 done；blocked/doing/done/cancelled 的合法迁移有表驱动测试。
- 删除/归档目标和计划不产生孤儿任务；并发状态更新不覆盖他人的新版本。
- 看板与列表使用同一统计口径，空态与失败态完整。

**退出标准**：不调用模型也能完成目标—计划—任务全流程，所有状态变化可追溯且依赖不失真。

## Phase 18 AI 计划与行动闭环

**目标**：把 Agent 接入 Action，但计划必须草案先行，写操作必须审批。

**范围**：list_tasks/get_task 读工具、create_goal/create_plan/create_task/update_task 写工具、计划草案编辑与确认、Dashboard 聚合。

**提交拆分**
1. `feat: 注册行动查询工具`
2. `feat: 实现 AI 计划草案生成`
3. `feat: 实现计划编辑确认与批量落库`
4. `feat: 注册行动写工具并接入审批`
5. `feat: 实现 Dashboard 目标与今日待办`
6. `test: 覆盖计划确认幂等与 Agent 越权`

**质量验证**
- 草案可增删改，确认前不出现在正式任务列表；重复确认不重复建任务。
- Agent 不能直接 approved，不能删除目标/计划，不能绕过依赖检查。
- 批量落库任一任务失败则整体回滚；审批参数与最终写入内容一致。
- “一个月学习 Go 并发”样本能结合记忆与知识生成草案，用户修改后形成真实任务链。

**退出标准**：从目标提出到草案、修改、审批、任务执行、Dashboard 进度全部闭环，越权路径有回归测试。

## Phase 19 Context 上下文工程

**目标**：基于真实长对话样本优化上下文，不在早期凭空调参。

**范围**：ctxbuild、分段预算、token 估算校准、conversation_summaries、摘要任务、上下文构成记录与调试视图。

**提交拆分**
1. `refactor: 收口对话上下文构建入口`
2. `feat: 实现上下文分段预算与裁剪`
3. `feat: 实现对话摘要生成与注入`
4. `feat: 实现上下文构成记录与调试`
5. `test: 建立长对话与约束保留回归集`

**质量验证**
- system/记忆/知识/历史/摘要各段实际 token 可查看，总预算不可突破。
- 连续 30 轮样本的 prompt_tokens 不随历史单调失控；否定约束与目标在摘要后仍保留。
- 摘要失败降级为安全截断且不阻塞对话；原消息永不删除。
- 估算值与真实 usage 的偏差有记录，模型调用失败不写伪用量。

**退出标准**：固定长对话评测通过，任何分支都不超预算；用户能知道本次回答使用了哪些知识与记忆。

## Phase 20 Insights 个人洞察

**目标**：先保证统计真实，再让模型做总结；没有数据时明确说没有。

**范围**：周期统计、insights、定时与手动生成、学习进度、知识覆盖与简单关联、Dashboard/Insights 展示。

**提交拆分**
1. `feat: 实现周期统计聚合与洞察模型`
2. `feat: 实现周期总结生成任务`
3. `feat: 实现学习进度与知识覆盖分析`
4. `feat: 实现洞察展示与 Dashboard 卡片`
5. `test: 覆盖统计口径周期边界与幂等`

**质量验证**
- 统计结果与 tasks/documents/memories 手工核对一致，UTC 周期边界明确。
- 同一周期重复生成按唯一约束更新或复用，不产生重复卡片。
- 空数据返回“暂无足够数据”，模型不得编造活动；模型失败不影响统计查询。
- 关联发现只基于真实向量/标签结果并展示依据，不宣称因果。

**退出标准**：日报/周报可自动生成且能手动重跑；所有数字有来源，所有建议能区分统计事实与模型判断。

**目标**：把已验证能力变成可部署、可备份、可排查、可持续维护的产品。

**范围**：后端与前端镜像、全栈编排、数据导出与备份恢复、运行指标、核心链路端到端回归、部署与使用文档。

**提交拆分**
1. `feat: 实现后端前端镜像与全栈编排`
2. `feat: 实现个人数据导出与备份能力`
3. `feat: 补充关键链路日志与运行指标`
4. `test: 建立核心用户链路端到端回归`
5. `test: 执行故障恢复与长稳验证`
6. `docs: 完善部署使用备份与接口手册`
7. `chore: 整理依赖并完成发布前检查`

**质量验证**

**退出标准**：文档命令逐条实测，核心链路自动化回归全绿，备份恢复真实演练成功，没有未登记的高优先级问题。

## 3.5 后置增强（不排期）

从原阶段移出、不占主线编号的能力。写清触发条件，避免“想起来就做”。

| 能力 | 原位置 | 现状 | 触发条件 |
|---|---|---|---|
| PDF 文本层解析 | P5 | 未实现，`.pdf` 返回 415 | 出现真实 PDF 导入需求，且样本以可提取文本层为主 |
| 网页正文抽取 | P5 | 未实现，无对应接口 | 需要把外部文章长期沉淀进知识库 |
| OCR 扫描件识别 | — | 未规划 | 有扫描件需求，且已独立评估 OCR 服务成本 |

**PDF 选型调研结论（2026-11-09，记下来免得重做）**：纯 Go 生态里中文 PDF 提取普遍脆弱。

- `ledongthuc/pdf`（BSD-3，631★，2026-10 仍在合并 PR，含 CMap 解码修复）是当前最优基线，短板是 Form XObject 内文本丢失、CID 字体缺 ToUnicode 时乱码；
- `Detective-XH/GoPDF`（BSD-3）是它的修复 fork，针对性改进了 CJK 与 ToUnicode 优先级，但 0★、单人、数月未更新，只适合做备选；
- `go-fitz`（AGPL-3.0 + cgo）、`unidoc/unipdf`（商业 license）不适合本项目；
- `pdftotext`（poppler-utils）质量最好，但引入系统包依赖，破坏“单个二进制即可运行”的部署形态。

**结论**：真要做得先用真实样本实测再定，不要按 README 选型。

## 4. 依赖与顺序约束

- **P1–3 是地基**：迁移、错误处理与前端请求约定不稳定，后续每个模块都会重复返工。
- **P4–6 先于 P7**：先有可靠文本与任务边界，再接向量，避免把解析故障和模型故障混在一起。
- **P8 先于 P9**：检索质量未达标时不能做 RAG，否则无法区分“搜错”与“答错”。
- **P10 先于 P11–12**：先有人工可修订的真相数据，再接自动提炼与召回。
- **P13 先于 P14–15**：最小对话闭环稳定后，才增加工具、预算、审批与恢复。
- **P16 复用 P6**：MQ 是增强唤醒与后台执行，不替代 jobs，不重写任务状态机。
- **P6 不占 `/tasks`**：系统后台作业的状态嵌在知识页；`/tasks` 留给 P17 的个人目标/计划/待办，两者不混用同一页面。
- **P17 先于 P18**：Action 自身规则正确后，Agent 才能通过 service 安全操作。
- **P19 放在真实对话之后**：用 P13–18 产生的样本调上下文，不提前做无效优化。
- **P20 靠真实数据**：没有知识、记忆和任务积累时，不做伪造洞察。
- **Redis 仍非必选**：只有真实瓶颈出现时单独评审，不因技术栈列表提前引入。

## 5. 阶段内工作方式

1. **开始前**：重读本阶段目标与上阶段验收记录，列出本轮不改的范围。
2. **实现中**：先补失败测试或最小复现，再实现；外部依赖的官方用法先确认再引入。
3. **自审时**：检查错误路径、资源关闭、context 传播、并发与重复执行，不只看 happy path。
4. **收尾时**：跑固定门禁和本阶段专项验证，更新进度与已知问题。
5. **发现跨阶段问题**：能小步修复就单独 fix；需要改设计时先停下当前功能，完成设计评审后再继续。

## 6. 变更管理

- 任何“提前实现后续阶段能力”的想法先记录，不直接进代码。
- 阶段范围可以缩小或继续拆，但不能通过删除测试、降低样本要求来宣布完成。
- 不允许以"先做最小实现、细节以后补"为由缩减阶段内已声明的范围；确需缩小，必须改写该阶段的范围与退出标准并写明原因，留半截界面或只有 API 不算完成。
- 相邻的小功能可以合并进同一阶段，但合并后仍要逐条对应六条完成标准，不能借合并降低验收。
- 阶段目标调整必须同步修改本文件、`docs/design/overview.md` 与 README 路线引用。
- 真实模型评测失败时先分类为检索、上下文、提示词、结构化输出或运行时问题，再进入对应修复提交，不盲目调参。
