# MindOS 开发记录

本文件记录**已经做了什么、为什么这么做、当时验证到什么程度**。

这里没有路线图，也不再有"下一步该做哪个阶段"：做什么、先做什么由用户决定。这份记录只负责三件事——同一件事不重复讨论、设计取舍有据可查、已知限制不会被忘掉。

历史条目里的 `Phase N` 是当时的编号，编号不再往后延伸。

---

## 1. 工程约定

1. **先设计后实现**：涉及数据模型、模块边界或执行语义时，先改 `docs/design/overview.md`，再写代码。
2. **不做占位实现**：要做的功能一次做全（含空态、加载态、失败态、重试与取消入口），不留"只有 API、界面以后再说"的半成品。确实超出范围的相关能力写进第 4 节，注明触发条件。
3. **小步提交**：一次提交只做一件事、可独立回滚，不把多个独立行为揉在一起。
4. **先正常后异常**：除了成功路径，还要验证参数错误、依赖不可用、重复执行和取消/恢复。
5. **不带债收尾**：编译通过不等于完成；声明的自动化测试、故障验证和文档更新全部做完才算。
6. **不拿真实模型做脆弱测试**：自动化测试用本地假 HTTP 服务或测试替身；真实模型只做可重复的冒烟与质量评测，不断言逐字回答。
7. **数据库不降级**：repository 与迁移测试使用真实 PostgreSQL/pgvector，不用 SQLite 替代，避免方言与并发行为失真。

## 2. 质量门禁

后端每次改动都执行：

```bash
cd backend
go build ./...
go vet ./...
go test -race -count=1 ./...
```

前端：

```bash
cd frontend
npm run lint
npm run test
npm run build
```

按改动内容补充相应测试层次：

| 层次 | 必须覆盖的内容 |
|---|---|
| 单元测试 | 纯函数、状态机、边界值、错误分支；bug 修复必须带回归测试 |
| 数据库集成测试 | 迁移、约束、事务、条件更新、并发领取、回滚；使用真实 PostgreSQL |
| HTTP 契约测试 | 统一信封、状态码、参数校验、错误码、request_id |
| 前端测试 | 关键交互、空态、加载态、失败态；不只测组件能渲染 |
| 故障注入 | 模型超时、进程重启、连接断开、重复消息、依赖宕机 |

### 一次改动收尾的标准

六条同时成立才算做完，缺一条都不算：

1. **功能闭环**：用户能在界面上走完全部路径，含空态、加载态、失败态；不是只有 API 可调。
2. **失败可解释**：每类失败有明确错误码与中文提示，不出现 `500 + internal error` 让人去翻日志。
3. **故障演练**：把依赖的故障真的制造一遍（停库、停 MinIO、`kill -9`、模型超时/限流），验证状态可恢复、不留半截数据，并把过程写进第 3 节。
4. **并发与重复**：双击、刷新重进、重复提交、并发操作都不产生脏数据，且有用例守着。
5. **测试与门禁**：单测 + 真库集成 + 前端用例齐备，`go build/vet/test -race` 与 `lint/tsc/test/build` 全绿。
6. **文档同步**：第 3 节写记录，`docs/design/overview.md` 同步，关键取舍落进代码注释。

**提交拆分**

2. `feat: 实现本地文件存储与内容哈希`
3. `feat: 实现 Markdown 与纯文本解析`

**质量验证**

**验收记录（2026-11-09）**

- 迁移：`go run ./cmd/migrate up` 在已有 Phase 2 的开发库上从版本 1 升到 2，`documents` 与 `document_chunks` 一次建全（含 `content_hash` 唯一索引、`(document_id, seq)` 唯一、`tsv` 生成列、`embedding vector(1536)`）。
- 接口实测（`HTTP_ADDR=:18080` 起服务，避开已被占用的 8080）：笔记与文件均返回 201；列表 `total=2`；分块 `[0,67)`、`token_count` 有值；错误路径返回 415（.pdf）、400（空笔记）、404（不存在）、409（同内容重复导入）。
- 偏移正确性：`[]rune(text)[start:end]` 逐字等于分块内容；中文与 emoji 按 1 个码点计；CRLF、无收尾围栏、超长无标点段落都有确定行为。
- 事务边界（真实库集成测试）：分块违反 CHECK 时整笔回滚，`documents` 不留空记录；重复 hash 翻译为 `ErrDuplicate`；删除文档时级联清空分块。
- 落盘失败补偿：写库失败时删除本次新写文件；内容已存在（`Reused`）时不删，避免把更早文档的原文删掉。存储按 SHA-256 内容寻址，重试不会产生副本。
- 门槛：`go build ./...` / `go vet ./...` / `go test -race -count=1 ./...` 全绿；前端 `lint` / `test`（24 用例）/ `build` 全绿。
- 与设计的两处偏差：① `GET /documents` 本阶段只做 `limit` / `offset`，`collection` / `tag` / `status` 筛选随 Phase 5 的标签能力一起做（没有写入方的筛选条件无法验收）；② 偏移单位改为**码点**而不是设计文档原写的"字符"，实现与文档已同步。
- 已知限制：分块不设重叠（等有召回评测数据再定）；`token_count` 是估算值（CJK 1 token/字，其余 4 字符/token），接真实分词器之后；知识页未做分块翻页（超过 100 块只显示前 100 块并提示）；窄屏布局仍未人工目视验收。

### Phase 5 文档管理可靠性（已完成，2026-11-09）

**目标**：把导入从“传一次就定型”变成可反复操作的文档管理。

**范围**：重复导入复用既有文档、删除、重索引、分类与标签筛选。**多格式（PDF、网页）已移出主线**，理由见文末「后置增强」。

**提交拆分**
1. `feat: 实现文档幂等导入与重复检测`
2. `feat: 实现文档删除与重新索引`
3. `feat: 实现分类标签与列表筛选`
4. `test: 覆盖重复导入、删除与重索引`

**质量验证**
- 相同内容重复上传返回既有文档（200，带 `existed: true`），不产生第二组分块，也不多存一份文件。
- 重索引用新结果整体替换：先算完新分块，再在同一事务里删旧插新；失败时旧数据完整保留。
- 删除在同一事务内清 documents（分块级联），提交后才删原始文件；文件删除失败只记日志，不回滚已提交的事务。
- 重复删除返回 404，不留孤儿行；同内容文档只有一条，删除不会误删他人的原文。

**退出标准**：文件与笔记两种来源都能重复导入、删除、重索引、打标签；重复上传、重复删除、连续重索引不产生孤儿文件或孤儿行。

**与原计划的偏差**：原计划含 PDF 文本层与网页正文抽取，2026-11-09 决定移出主线。原因是它们必然引入首个第三方解析依赖（或系统包），而收益与当前主线（检索、Agent）无关，属于产品化之后的可选增强。

**验收记录（2026-11-09）**

- 迁移：**本阶段不需要新迁移**。`collection` / `tags` 在 0002 里就一次建全（含 `tags` 的 GIN 索引），本阶段只是把它们从"预留列"变成真正读写。
- 幂等导入实测（`HTTP_ADDR=:18080`）：同内容第二次 `POST /documents/note` 返回 **200 + `existed:true`**，`id` 与首次相同、标题仍是首次的标题；首次返回 201。文件导入同理，且不产生第二份原文件。
- 标签与分类：`text[]` 在 GORM 下**必须自定义类型**——`[]string` 写入会报 `expression is of type record`、读取会报 `unsupported Scan ... into *[]string`，两条实测结论写在 `internal/knowledge/string_array.go` 文件头；`Value`/`Scan` 成对实现并有往返用例守着引号、反斜杠、空格、中文。
- 筛选实测：`?tag=go` 命中 1 条，`?tag=nope` 返回空列表且 `total=0`（不是 404），`?status=bogus` 返回 400 并列出合法取值；列表与总数共用同一份条件。
- PATCH 实测：`{"collection":"","tags":["归档"]}` 清空分类（落库为 NULL）并替换标签；`{}` 返回 400；不存在的 id 返回 404。
- 删除实测：返回 `200 + {"id":4}`，第二次删除 404；分块由外键级联删除（真实库集成测试断言无孤儿行）；文件删除失败只记 warn、不回滚已提交的事务（单测制造删除失败）。
- 重索引实测：`POST /documents/4/reindex` 返回重算后的 `chunk_count`；替换失败时旧分块完整保留，缺原文时返回 409 而不是 500。
- 门槛：后端 `go build ./...` / `go vet ./...` / `go test -race -count=1 ./...` 全绿；`MINDOS_TEST_DSN` 指向真实 PostgreSQL 时 7 个集成用例通过（新增 5 个）；前端 `lint` / `test`（31 用例）/ `build` 全绿。
- 三处由本阶段定下的语义：① 幂等命中**不做任何写入**（不合并标签），改元信息走 PATCH——否则"同内容即同一条记录"这个前提会失效；② 删除返回 `200 + {"id":n}` 而不是 204，保持所有响应都走统一信封；③ 缺原文重索引映射为 409，它是数据状态问题而非参数错误。
- 前端按约定先拆分再加功能：`pages/knowledge.tsx`（319 行）只做编排，列表、详情、筛选栏、笔记表单、格式化各自成文件，`CONVENTIONS.md` 的示例已同步。
- 已知限制：`collection` 没有建索引（单用户数据量下全表扫描可接受，真变慢时再加）；重索引是同步请求，10 MiB 文档会占住一条连接，P6 异步化后一并解决；网页导入仍未接。

**回补项（2026-11-10 登记，进入 Phase 6 之前完成）**

按"只补已知尾巴、不返工旧阶段"的决策，本阶段遗留一个确定缺口：

- 文件上传入口没有分类/标签输入框，只有笔记表单与详情页能设置——同一功能在两个入口能力不一致，属于本阶段功能没做完整。
- 单独一笔 `feat: 文件上传支持设置分类与标签`，含前端用例（提交时带上 collection/tags、留空时不传、非法标签沿用既有 400 文案）。
- 补完后此阶段无其他回补项；不回头补 P1–P4 的视觉与窄屏人工验收。

**回补验收记录（2026-11-10）**

- 交互改为两步：选中文件先落到确认面板（显示文件名与大小、分类、标签、要保存的标签预览），点「开始导入」才发请求；取消则清空待导入文件、不发请求。理由：选完即传等于没有机会填元信息，而笔记表单与详情页都能填。

- 已知限制：上传面板不校验文件类型与大小，仍由后端返回 415 / 413 后由页面提示。

### Phase 6 本地异步任务（已完成，2026-11-10）

**目标**：将耗时导入与重索引移出 HTTP 请求，靠 PostgreSQL 建立可恢复的任务语义，并把任务状态做成知识页里能看、能操作的功能，不急于引入 MQ。

**范围**：jobs 表与状态机、进程内 worker、条件领取与租约续约、退避重试与错误分类、取消传播、启动与周期补扫、文档导入/重索引切换为 202 + job_id、知识页内的任务进度与失败原因展示、取消与手动重试入口。

**边界**：任务状态**嵌在知识页**（文档行内状态、详情页错误与重试），不占用 `/tasks` 页面——`/tasks` 规划给 Phase 17 的个人目标/计划/待办，与系统后台作业不是一回事。本阶段不做通用任务中心，不接 MQ。

**提交拆分**
1. `feat: 新增异步任务模型与迁移`
2. `feat: 实现任务条件领取与租约续约`
3. `feat: 实现进程内 worker 与优雅停止`
4. `feat: 实现任务补扫与崩溃恢复`
5. `feat: 文档导入与重索引切换为异步任务`
6. `feat: 实现任务重试取消与失败原因接口`
7. `feat: 知识页展示任务进度并支持取消重试`
8. `test: 覆盖并发领取、故障注入与进程重启恢复`

**质量验证**
- 多 worker 并发时同一 job 只被一个领取；重复提交有 dedupe 行为（部分唯一索引兜底，不靠应用层先查后插）。
- worker 宕机后过期租约可被接管；补扫不只跑在启动时，周期补扫也要覆盖"别的实例还挂着"的场景。
- 续约失败（影响 0 行）时 worker 必须放弃执行，不允许两个 worker 同时写同一文档的分块。
- 取消能传播到解析过程；达到 max_attempts 后停止重试并保留错误码；`ErrUnsupportedType` 这类不可恢复错误直接 failed，不空转重试。
- HTTP 202 返回 document 与 job_id；幂等命中仍返回 200 + existed，不新建任务。
- 页面上传后立即看到"处理中"，失败行显示中文原因并提供重试/取消；刷新页面后状态不错乱，轮询在终态自动停止。

**故障演练（必须实际执行并记录）**
1. 任务跑到一半停 PostgreSQL：job 可解释地失败或等待，恢复后能被重试到终态。
2. 任务跑到一半停 MinIO：原文读取失败有明确错误，文档不处于"看起来成功"的状态。
3. `kill -9` 服务进程再重启：running 任务经租约过期回到 queued 并跑完，不出现永远 running。
4. 运行中点击取消，再刷新页面：状态一致，不回到 running。

**退出标准**：上述四类故障演练全部通过且任务状态可解释、可恢复；六条完成标准同时满足。

**验收记录（2026-11-10）**

- **迁移**：`0003_jobs`，一次建全而不是逐阶段加列。三处约束/索引各有明确用途：状态机 CHECK、部分唯一索引 `(kind, dedupe_key) where status in ('queued','running')` 负责去重、`(run_after)` 与 `(lease_expires_at)` 两条部分索引让领取与补扫只扫"待办"。
- **契约**：`POST /documents`、`/documents/note`、`/documents/:id/reindex` 均改为 **202 + job_id**，文档先落 `pending` / `indexing`；`POST /documents/:id/cancel` 返回 200 + 文档状态，没有进行中的处理时 409。幂等命中仍是 200 + `existed`，且不建任务。
- **队列语义**：领取用一条 `UPDATE ... WHERE id = (SELECT ... FOR UPDATE SKIP LOCKED LIMIT 1)`，判断与改状态同一条语句；`attempts` 在领取时 +1（崩溃那次也算尝试）；心跳每 `lease/3` 一次并回报状态；退避 3s·2^n 封顶 5 分钟并叠加 ±25% 抖动；不可恢复错误（类型不支持、编码错误、元信息非法、原文丢失、文档不存在、任务类型未注册）直接判失败，不占重试名额。
- **任务与文档的两次同事务写入**：`CreateWithJob`（文档 + 任务）与 `FinishImport`（换分块 + 置 ready）。前者避免"有文档没任务"，后者避免"显示成功但内容是空"。
- **错误可解释**：`documents.error_code` 与 `jobs.last_error_code` 记同一个码（业务错误实现 `JobErrorCode`，worker 只搬运）。已有码：`unsupported_type`、`empty_document`、`not_utf8`、`invalid_metadata`、`source_missing`、`storage_unavailable`、`document_not_found`、`cancelled`、`process_failed`。前端详情页在失败时就地显示原因。
- **故障演练（2026-11-10 20:19 起，隔离库 `mindos_drill`，服务跑在 `:18080`）**

| 演练 | 操作 | 观察结果 |
|---|---|---|
| kill -9 | 导入返回 202 后立刻 `kill -9`，重启 | 任务从 `queued/a0` 继续，重启后 `succeeded/a1`，文档 `ready` |
| 执行中死亡 | 直接插入一条 `running` + 租约过期 10 分钟的僵尸任务，重启 | 补扫 1 次将其收回，另一 worker 领走并 `succeeded`，文档 `ready` |
| 停 PostgreSQL | 服务运行中 `docker stop mindos-postgres`，2 秒后恢复 | 进程不退出；`healthz=200`（存活不看依赖）、`readyz=503`；worker 12 次领取失败只 warn；恢复后 `healthz=200`、导入返回 202 |
| 停 MinIO | 上传文件后 `docker stop mindos-minio`，再发起重索引 | 重试 2 次后任务 `failed`、`attempts=3`，任务与文档的 code 都是 `storage_unavailable`；恢复 MinIO 后重新切分成功，`ready` 且 `chunk_count=1` |
| 运行中取消 | 导入后立刻取消 | 返回 200；任务 `cancelled`；文档 `failed` + `cancelled` + 0 分块，两秒后状态不再变化 |

- **演练中修掉的两个真实缺陷**：① 原先取消直接写 `failed`，若 worker 刚好写完分块，会留下"失败但有分块"的半状态；改为运行中只标 `cancelling`，终态由 worker 停下后回调写，回调发现分块已存在则保留成果置 `ready`。② 原先 MinIO 不可用被记成 `handler_error` / `process_failed`，看不出是存储问题；新增 `ErrStorageUnavailable` 与 `storage_unavailable` 码，并让任务表复用同一码。
- **门禁**：后端 `go build ./...` / `go vet ./...` / `go test -race -count=1 ./...` 全绿；带 `MINDOS_TEST_DSN` 时真实库集成用例通过（job 包新增退避、取消、接管；knowledge 包新增两段式、失败原因、取消收尾）。前端 `lint` / `test`（41 用例）/ `build` 全绿。
- **已知限制**（2026-11-10 当时的状态，已被下方「架构调整」取代，保留作历史记录）：① worker 只在进程内，多实例靠租约互斥而不是分区，规模上去后需要按 kind 分队列；② 空闲时仍按 `JOB_POLL_INTERVAL`（默认 500ms）轮询，当时计划由 MQ 唤醒（2026-11-14 已实现）；③ 按 `payload->>'document_id'` 取消会全表扫 jsonb，单用户量级可接受，任务表变大后需要加表达式索引；④ kill -9 演练中任务恰好已完成（`queued` 状态被杀），"执行中死亡"的真实接管由僵尸任务那一条覆盖；⑤ 取消与完成赛跑时，若内容已写完则保留成果（`ready`），此时任务记 `cancelled`、文档记 `ready`，两者语义不同但都如实。

#### 2026-11-14 架构调整：outbox + RabbitMQ 提前落地，jobs 表已删除

上面那套"表当队列 + 进程内 worker + 租约心跳"被整体推翻，P16 的核心部分提前到这里。理由不是它坏了，而是**它把两件生命周期完全不同的事放在了一张表里**：

| 关注点 | 该活多久 | 该由谁管 |
|---|---|---|
| 进度与历史（这文档处理到哪一步、失败原因是什么） | 长期，要能查、要留审计 | `tasks` 表 |
| 投递（这条消息发出去没有、重试几次） | 很短，发完就该删 | `outbox` 表 |

`jobs` 表同时扮这两个角色，于是删不掉、查不清，还得为"发过的消息"维护补扫。拆开之后各自的规则简单得多。

**新链路（三条，缺一不可）**

```
受理  事务写 documents(pending) + tasks(pending) + outbox(待发)  → 202 + message_id
投递  relay 每 200ms 扫 outbox 待发 → RabbitMQ             → outbox.status=1
执行  消费者按 topic 分发 → 更新 tasks 状态 → 写 documents → 标记已消费
兜底  reaper 每 30s 对账：卡住的 task 重投，过期消息清理
```

**删掉的东西**：`internal/job` 整个包（worker 循环、条件领取、租约续约、心跳、退避重试、补扫，实现与测试各约 1100 行）、`jobs` 表（迁移 `0007`）、`JOB_LEASE` / `JOB_POLL_INTERVAL` / `JOB_RECOVER_INTERVAL` 三项配置。

**保留下来的语义**：重试上限 3 次、退避 3s·2ⁿ 封顶 5 分钟、永久错误不占重试名额（改为 `knowledge.IsPermanent` + 消费端提前收尾）、取消分"排队中直接取消"与"运行中标记取消中"两条、终态由执行方写而不是请求方抢先写。

**契约变化**：受理响应 `job_id`（内部自增）→ `message_id`（uuid）。消息编号跨进程稳定、消费端用它去重、日志里能直接对上。

**新增的已知限制**（替代原来那五条）：

1. 容忍"至少一次"：消息可能重复投递，靠 `tasks.MarkRunning` 的条件更新（`WHERE status='pending'`）做执行闸门，所以处理函数必须可重跑。
2. 消费端崩溃留下的 `running` 任务，broker 不会重投（消息已 ack），只能靠 `reaper` 在 `REAPER_STALE_AFTER`（默认 2 分钟）之后捞回——最长延迟就是这两个参数之和。
3. 单队列、无优先级：`document.import` 与 `document.reindex` 排同一条队。需要优先级时要拆队列或加表字段。
4. 同文档并发仍靠 `tasks_active_uniq` 部分唯一索引挡住，`msg_key` 目前只用于排查与按对象查历史，没有做分区消费。
5. `outbox` 与 `consumed_messages` 只增不减的时间窗是 `REAPER_RETENTION`（默认 7 天），清理是分批的，积压很多时要多轮才删净。
6. **broker 只在启动时建连**：中途重启需要重启进程才能接上。期间受理照常返回 202，消息安全停在 outbox（`ErrQueueUnavailable` 不消耗重试次数、不判死），恢复并重启进程后自动补发。自动重连留给 P16。

**故障验证**（隔离库 `:18082`，`REAPER_INTERVAL=5s`）：

| 场景 | 观察 |
|---|---|
| 正常导入 | `202` + `message_id` → `tasks succeeded` → 文档 `ready`，队列 0 积压 |
| 重索引 | `202` + 新 `message_id` → `indexing` → `ready` |
| 原文指向不存在对象 | 文档 `failed/source_missing`，任务 `failed/source_missing`，`attempts=0`（永久错误未占重试） |
| 手造 `running` 且 5 分钟未动 | `reaper` 重投 1 次 → `succeeded/attempts=2` |
| 导入在途取消 | 文档 `failed/cancelled`，任务 `cancelled` |
| 清理边界 | 只删"已投递且过期"；待发与投递失败的一条不删 |

**门禁**：后端 `build` / `vet` / 全量 `test -race`（含 DSN 集成）全绿，新增 `reaper` 包的 5 个集成用例；前端 `tsc` / `lint` / 42 用例全绿。

## 4. 未做的事与结论

暂不实现、但已经有判断的能力。写清触发条件，避免"想起来就做"或"重新调研一遍"。

| 能力 | 现状 | 触发条件 |
|---|---|---|
| PDF 文本层解析 | 未实现，`.pdf` 返回 415 | 出现真实 PDF 导入需求，且样本以可提取文本层为主 |
| 网页正文抽取 | 未实现，无对应接口 | 需要把外部文章长期沉淀进知识库 |
| OCR 扫描件识别 | 未规划 | 有扫描件需求，且已独立评估 OCR 服务成本 |

**PDF 选型调研结论（2026-11-09，记下来免得重做）**：纯 Go 生态里中文 PDF 提取普遍脆弱。

- `ledongthuc/pdf`（BSD-3，631★，2026-10 仍在合并 PR，含 CMap 解码修复）是当前最优基线，短板是 Form XObject 内文本丢失、CID 字体缺 ToUnicode 时乱码；
- `Detective-XH/GoPDF`（BSD-3）是它的修复 fork，针对性改进了 CJK 与 ToUnicode 优先级，但 0★、单人、数月未更新，只适合做备选；
- `go-fitz`（AGPL-3.0 + cgo）、`unidoc/unipdf`（商业 license）不适合本项目；
- `pdftotext`（poppler-utils）质量最好，但引入系统包依赖，破坏"单个二进制即可运行"的部署形态。

**结论**：真要做得先用真实样本实测再定，不要按 README 选型。

**Redis 仍非必选**：只有真实瓶颈出现时单独评审，不因技术栈列表提前引入。

## 5. 工作方式

1. **开始前**：重读相关章节与最近一次记录，列出本轮不改的范围。
2. **实现中**：先补失败测试或最小复现，再实现；外部依赖的官方用法先确认再引入。
3. **自审时**：检查错误路径、资源关闭、context 传播、并发与重复执行，不只看 happy path。
4. **收尾时**：跑固定门禁和专项验证，更新第 3 节与已知限制。
5. **发现相邻问题**：能小步修复就单独 fix 并记录；需要改设计时先停下当前功能，完成设计评审后再继续。
